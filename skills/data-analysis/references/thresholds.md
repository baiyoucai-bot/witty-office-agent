# 判定阈值

`scripts/profile_table.py` 用的默认线。业务有自己的口径就按业务的，但要在交付物里写明改了哪条、为什么。

WARN 是「要解释」，FAIL 是「不解释就不能往下算」。两者都不自动删数据。

## 空值

| 判定 | 默认线 | 含义 |
|------|--------|------|
| WARN | ≥ 5% | 比正常多，查原因 |
| FAIL | ≥ 30% | 太稀疏，不填补就别参与计算 |

例外要先说清楚再放宽：

- 本来就选填的字段（备注、第二联系人）：WARN 放到 50%。
- 只对部分记录适用的字段（专项标记、活动参与）：先写清预期空值率，再判。
- 上游补齐的派生字段（区域、分类）：WARN 15%，FAIL 60%。

`0` 和空值不是一回事。先确认这一列的 0 是真值还是「没填」的替身，再决定怎么算均值。

## 重复

| 检查 | 默认线 |
|------|--------|
| 整行重复 | > 0% 查原因；> 1% 判 FAIL |
| 主键重复 | > 0% 就要解释；是版本化就写明按哪列取最新 |

主键重复最常见的后果是合并放大，见 `pandas-traps.md`。

## 离群

| 方法 | 线 |
|------|-----|
| IQR | 落在 Q1 − 1.5×IQR 以下或 Q3 + 1.5×IQR 以上 |
| Z 分数 | \|z\| > 3 |

离群只标记，不自动剔除。每个都要归到一类：

- **真信号**：确实存在的极端值（一笔大额合同、一次检修高峰）。
- **数据错误**：单位不一致、上游 bug、测试数据混入。
- **哨兵值**：`-1`、`9999`、`1900-01-01` 这种「未知」编码。当成数值算会污染均值。

判成数据错误才可以改或排除，并在交付物里写明影响了多少行。

## 数值范围

按列的业务含义先卡一遍，比任何统计量都先发现问题：

| 列类型 | 规则 |
|--------|------|
| 年龄 | 0 ≤ x ≤ 120 |
| 金额、电量、工时 | ≥ 0；允许负数就写明负值代表什么（冲抵、退单、反送电） |
| 比例、率 | 0 ≤ x ≤ 1，或 0–100；先确认是哪一种编码 |
| 时间戳 | 在 [系统上线日, 今天 + 1 天] 之间 |
| 枚举、代码 | 取值落在已知集合内；出现新值先问，不要自己归类 |

单位混装是最容易漏的一类：同一列里既有「万元」又有「元」，统计量全都正常，结论全错。量级差 3 个数量级以上的分组要单独看。

## 偏度

| \|skew\| | 判定 | 处理 |
|---------|------|------|
| < 0.5 | 近似对称 | 不用处理 |
| 0.5 – 1 | 中度偏 | 记一笔；均值和中位数一起报 |
| > 1 | 明显偏 | 用中位数和分位数，不要只报均值 |
| > 2 | 极偏 | 先查离群和单位，再谈变换 |

偏态数据只报均值会误导。分位数（p50 / p90 / p95）通常比均值更贴业务。

## 相关

| \|r\| | 处理 |
|------|------|
| ≥ 0.8 | 标为强相关；两列不要同时进模型 |
| ≥ 0.95 | 基本是同一个量的两种写法，留一个 |

反过来也要看：本该相关的两列（电量与费用、工单量与工时）相关性接近 0，通常是筛选条件或连接键错了，不是发现了新规律。

相关系数默认只看线性关系，也只对数值列有意义。对分类列用交叉表，不要先编码成 0/1/2 再求相关。

## 时间覆盖

- 最新一条记录距今多久？超出预期滞后就先问数据是否跑完。
- 按天/周计数有没有断档（上游停了）或尖峰（补数、重跑）。
- 跨期比较的两段，口径和数据源必须一致。中间换过系统就不能直接比。
