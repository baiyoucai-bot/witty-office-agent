# 资料分类

一份类型表 + 一个目录进，**每个单元一个类型 + 判定依据**出。只读原文件，绝不移动、复制、改名。

## 何时用

调用方给了一份现成的类型表（JSON，通常几百条），要把某个目录下的文件对到这些类型上。
要写新的分类体系不走这里；只想看看目录里有什么用 `ls`。

## 硬规矩

1. **类型只能来自类型表**。表里没有的 id 一个都不许出现。判不出来就落 `_待分类`，不许编造。
2. **用途优先于形态**。文件属于哪类取决于它「为什么存在」，不取决于它「长什么样」。投标目录下的合同是投标资料，不是合同。
3. **只读**。工具产出的是一份映射报告，原目录一个字节都不动。
4. **每条判定都要有依据**。`evidence` 空的判定等于没判，要打回重来。
5. **拆分件是一个单元**。1.png / 2.png / 3.png 若确认同源，只出一个类型。

## 怎么跑

窗口里直接调 `classify_files`：

```
classify_files(root="/path/到/资料目录", taxonomy="/path/到/类型表.json")
```

`taxonomy` 可以给 JSON 文件路径，也可以直接给 JSON 字符串。形状容忍度较高：类型对象数组、`id → 名称` 字典、带 `children` 的嵌套子类都能吃；id 字段认 `id` / `code` / `编号`，名称认 `name` / `名称` / `title`。

脚本侧用同一套逻辑：

```bash
uv run python skills/file-classify/scripts/classify.py <目录> --taxonomy 类型表.json
```

库里调用：

```python
from witty_agent.plugins.file_classify import classify_directory   # 同步
from witty_agent.plugins.file_classify import aclassify_directory  # 异步，已在事件循环里用这个

summary = classify_directory(root, taxonomy, out_dir=out, limit=50, concurrency=4)
```

批次并发跑，`concurrency` 卡住同时在飞的模型调用数（默认 4）。网关扛不住就调小。

## 先小批试跑

**第一次对一个新目录跑，一定先加 `limit`**（脚本用 `--limit 30`，工具用 `limit=30`）。
先看 30 个单元的 `report.md`，确认判定口径对了再放开跑全量。几百个文件全跑完才发现口径错，等于白烧一遍 token。

试跑要重点看四件事：

- **待分类比例**。超过 15% 说明类型表描述太糊，或者证据不够，不是模型不行。
- **错分的方向**。看 `evidence` 里命中的是 `path:` 还是 `content:`。被内容带偏（该判投标却判成合同）是最常见的一类，改 `file_classify_system` 的「用途优先于形态」那一节补例子。
- **分组对不对**。`groups.jsonl` 里 `merge=false` 的组是模型主动拆开的，`group_conflict` 非空的是它觉得合错了。两者都要抽查。
- **名-文一致性**。抽几个 `evidence` 里只有 `name:` 证据、没有任何 `path:` 业务环节命中的高置信度单元，打开原文核对文件名没写错。这类「文件名孤证」按口径应该进第二轮核验；大量停留在第一轮说明「孤证不定案」那条没被执行，去改 `file_classify_system` 第四节。

## 三个阶段

### 1 候选分组

同目录 + 主干相同 + 只有编号不同的文件被拢成候选组（`1.png`、`扫描件_01.pdf`、`第3页.jpg` 这些都认）。
这一步纯靠命名，只是形式线索，**不是结论**。

### 2 分组确认

模型读每组前几个成员的正文，判断是不是同一份资料拆开的：正文跨文件接续、页码连续、封面只在第一份、签章只在最后一份 → 合并；各自有独立文号和签章、相对方不同 → 拆开。拿不准倾向于拆开。

图片没有可用文本时只能凭编号推断，这种组的 `confidence` 会低于 0.5 并注明「仅凭命名推断」，值得人工抽查。

### 3 两轮判定

- **第一轮**给完整路径、文件名，外加每个单元头成员正文开头的一小段「标题行」（默认 160 字，`title_chars` 调节，0 关闭）。标题行不是用来判类型的，是用来**核验文件名**的：文件名是人写的，可能写错——名为「合同.pdf」正文却是验收单的文件，靠标题行在这一轮被察觉。路径加文件名够用（且标题行不矛盾）就直接定；标题行与文件名不符、或路径全是无业务含义容器而文件名成了孤证的，模型会把 `need_content` 置 true 转入第二轮核验。
- **第二轮**只处理第一轮标了 `need_content` 或置信度低于 `min_confidence`（默认 0.6）的单元，附上正文摘录复判。

图片和纯扫描件抽不出文本，标题行只会显示「无法抽取文本」，文件名写错无从核验——这类文件仍只能靠路径和命名推断，要接 OCR 或视觉模型才能补上这一环。

绝大多数文件在第一轮就该定下来。如果第二轮的比例超过一半，多半是类型表的名称和说明太抽象，先去改类型表，别去调批次大小。

## 产物

结果落在 `out_dir`（默认 `WITTY_HOME/file_classify/<目录名>`）：

| 文件 | 是什么 |
|------|--------|
| `results.jsonl` | 真源。一行一个单元：类型、置信度、依据、推理、成员文件、哪一轮定的、是否最终 |
| `groups.jsonl` | 拆分件的合并/拆开决策及理由 |
| `report.md` | 给人看的，按类型分组列出全部单元和判定依据 |

`results.jsonl` 和 `groups.jsonl` 是**每批追加**的，跑到一半就能看到已完成的部分；`report.md` 是全部跑完才写一次。中途断了直接重跑同一条命令即可续上，要推翻重来加 `--no-resume`。

同一个 `unit_id` 可能出现两行：第一轮写一条初判，第二轮读完正文再写一条改写它。**`final` 字段区分**——`false` 是还会被改的初判，`true` 是最终结论。读回时按 `unit_id` 取最后一条。

库调用要实时拿结果的话别去轮询文件，传 `on_result` 回调，每批判完直接给你该批的结果行：

```python
classify_directory(root, taxonomy, on_result=lambda rows: upsert(rows))
```

回调里抛异常只记 WARN 不中断——结果已经落盘，下游炸了不该让整轮白跑。

## 改口径

**判定规则全部在 `config/prompts.toml` 的 `file_classify_*` 里，不要改 `plugins/file_classify.py`。**

常见的改法：

- 错分方向固定（总把某类判成另一类）→ 改 `file_classify_system` 第二节，把这个反例补进去。
- 某类业务的目录命名习惯特殊 → 改第二节里「目录名是否表达用途」那两行的词表。
- 合并太激进或太保守 → 改 `file_classify_group_system` 的两组证据。
- 第二轮触发太多 → 改第四节 `need_content` 的判据，或调高 `min_confidence` 反而会更多，注意方向。
- 写错的文件名没被察觉 → 先确认 `title_chars` 没被关掉，再改第三节「标题行核验文件名」和第四节「孤证不定案」两处的措辞补例子；标题行太短抓不到标题就调大 `title_chars`。

改完重跑试跑集对比，别直接上全量。
