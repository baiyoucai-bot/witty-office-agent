# Long Document

几万字的工作文档当成**工程**写，不当成一次模型输出。可研、详设、概设只是章节清单（profile），循环相同。

一页纪要 / 公函走 `office-document`；红头文件走 `word-docx` 的 `gongwen.py`。
成稿后用户要可编辑汇报 PPT：切 `witty-ppt-skills`，数字只认本报告，优先整份 `pptx_render`。

写法借鉴了公开案例，但只收**通用循环**，不收它们的产品壳：Stanford STORM / GPT-researcher 的「先锁提纲再按节扩写 + 来源账」；Karpathy LLM Wiki 的「工作区即真相」；Anthropic 办公技能的「确定性脚本抓静默失败」；学术综述的证据驱动写法「开写前盘料、样章先行、缺证据定向回补、整合审计、正文锁定后再制图」。不引入多角色调研团、不默认上网检索、不收投稿/期刊那套壳。依据见 `references/method.md`。

## 硬规矩

1. **一轮一章。** 运行时 `max_tokens` 装不下整本。写完一章跑校验，先改 `continuity.md`，再写下章。
2. **提纲是结构真相。** `outline.md` 有的章，`chapters/<slug>.md` 必须有；标题必须一致。
3. **数字带来源、关键数字进账。** 出处写成 `[cite:id]`，关键金额/规模写成 `[num:id]`。id 必须分别在 `sources.toml` / `ledger.toml`。没来源就写「待核实」，不要编制度条文。
4. **术语只有一种写法。** 登记在 `glossary.md`，正文不要换简称。
5. **下一章不准打开全书。** 只打开提纲、本章、相邻章标题、`continuity.md` 上一节、`ledger.toml`、`sources.toml`。
6. **写满预算，该有表就得有表。** 提纲行尾的 `~N字` 是本章字数预算、`+N表` 是最少表格数，`check_doc` 都按 FAIL 判。投资、效益、风险、进度、选型这类内容**光靠叙述说不清口径**——同样一句「投资较大」，摆成分项表才看得出钱花在哪、占比多少。写不满不是「精炼」，是没写完。
7. **「待核实」是留给查得到却没查的事，不是万能挡箭牌。** 可研阶段拿不到正式报价是常态，行规是**给出测算口径的估算值并注明以询价招标批复为准**，不是把每个数字都写成【XX】。一份没有投资表、没有总投资数的可研不成立。测算就写清依据（按什么基准、什么假设、什么年限），让人能复核；真正无从测算的（批复文号、牵头部门、正式清单）才写「待核实」。
8. **样章不过不量产。** 锁完提纲先写证据最密、写法最有代表性的一章当样章，口径、表样式、测算依据的写法、论证深度都在样章上定死。样章没过就修证据或修写法，改的是样章这一章，不是接着往下写——二十章写完才发现口径不对，返工比重写还贵。
9. **图放在正文定稿后画。** 正文没过整合审计前，图只写题注和 `[@fig:]` 占位，不生成图片文件。正文一改，图就作废，先画就是白画。表格是正文的一部分，照常随章写。

## 七步

### 1 起工程

```bash
<沙箱 Python> <技能目录>/scripts/init_project.py --name <项目名> --root <目录> --profile 可研
```

`--profile` 可选 `generic` / `feasibility` / `outline-design` / `detailed-design`，或中文别名 可研 / 概设 / 详设。幂等，已有文件不覆盖。

用户给了旧稿：先抽成文本，再登记，不要对着二进制改。

```bash
<沙箱 Python> <word-docx>/scripts/extract_text.py --input 旧稿.docx --output 工程/sources/旧稿.md
<沙箱 Python> <技能目录>/scripts/import_source.py --project <工程> --input 工程/sources/旧稿.md --id draft --title 用户旧稿
```

### 2 盘料、锁提纲

先把手头材料全部登记进 `sources.toml`（旧稿、批复、报价、制度文件），再改 `outline.md`。用户给了目录就严格按目录，不要自行加章。没有目录就用 profile 的必含章。

锁提纲前对着章节清单过一遍：**每一章的料在哪。** 有料的章标得出 `[cite:id]`；没料的章分两种——查得到的列成**回补清单**报给用户（要什么、给哪章用），真拿不到的按硬规矩 7 处理（测算口径 / 待核实）。料撑不起一整章的，砍章或并章，不硬写。

### 3 样章先行

从提纲里挑**证据最密、最能代表全书写法**的一章先写（可研通常是投资估算或技术方案，不是概述）。写完跑单章校验：

```bash
<沙箱 Python> <技能目录>/scripts/check_doc.py --project <工程目录> --chapter <slug>
```

然后对着样章自查三件事：数字是否都有 `[num:]`/`[cite:]` 且口径能复核、表格样式和测算依据列是否成立、论证深度是否配得上字数预算。用户在场就把样章给用户过目再往下。

样章通过后，它的口径、表样式、术语写法就是后续所有章的模板；不通过就修证据或修写法，重写样章，**不要带着问题量产**。

### 4 分章写

每个 `chapters/<slug>.md` 以 `# 标题` 起头，标题与提纲一致。写完立刻在 `continuity.md` 追加 `## slug`：主张、用过的 `[num:id]`、待核实、接下章的一句。

表格用标准 Markdown，前一行写题注，正文用 `[@tbl:标签]` 引用（导出成 Word 的 SEQ 自动编号 + REF 交叉引用）：

```markdown
表: 投资分项估算（测算口径，以询价招标批复为准） {#tbl:invest-breakdown}

| 序号 | 科目 | 估算金额（万元） | 占比 | 测算依据 |
|---|---|---|---|---|
| 1 | 硬件与算力 | 780 | 30% | 按 8 卡推理集群 + 存储扩容询价区间中值 |
| 2 | 数据工程 | 520 | 20% | 按 12 个源系统 × 接入治理人月单价 |
| 合计 | — | 2600 | 100% | — |
```

每张表都要有**测算依据**或**数据来源**列，否则表里的数字和正文里那句「投资较大」没区别。

写作中发现缺证据，**定向回补**：把缺的那一项（哪个数、哪份文件、给哪章）记进 continuity 的待核实，凑齐一批问用户或查 sources/，只补缺口，不推倒重搜。回补到了就回责任章把「待核实」换成实数。

### 5 校验

```bash
# 逐章循环：只看刚写完这一章
<沙箱 Python> <技能目录>/scripts/check_doc.py --project <工程目录> --chapter <slug>
# 结构齐了：全工程
<沙箱 Python> <技能目录>/scripts/check_doc.py --project <工程目录>
```

查缺章、标题漂移、悬空 `[cite:]` / `[num:]` / `[@fig:]`、术语、待核实、字数预算、交接节。FAIL 必修。

### 6 整合审计（结构齐了再做）

打开 `continuity.md` + `ledger.toml` + 提纲，按五项过：**术语**只有登记写法、**论断**前后章不打架、**重复**同一段论述不在两章各写一遍、**引用**待核实没有假装写完、**衔接**每章开头接得上上一章交接的那句。脚本只抓得住账本对得上，这五项靠人/模型读交接。

发现实质性冲突（两章口径不同、结论互斥），**回到责任章节改**——谁的主张错了改谁，连带更新该章在 `continuity.md` 的交接节，再跑一遍全工程校验。不要在后面的章里绕着写，更不要全书重排。

### 7 制图、导出

正文和引用账过审后才生成 `assets/` 里的图片，替掉占位路径，跑一遍全工程校验确认 `[@fig:]` 都落地。然后导出：

```bash
<沙箱 Python> <word-docx 技能目录>/scripts/report.py --project <工程目录> --output <路径.docx> --toc
```

先 `outline.py` 核标题层级。不要用 pandoc 把 md 转一遍当定稿。

## 交付

报工程路径、校验结论、导出文件、未核实项。不要复述过程。
