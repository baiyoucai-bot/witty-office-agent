# NL2SQL 第 1 阶段：意图落地与模式链接

**这一阶段错了后面全错。** 表选漏一张、值写法差一个字，SQL 写得再漂亮也是编数据。

产出一份「链接后的模式」：几张表、哪些列、连接键是什么、问句里的词对应库里的哪些真实值、口径怎么定。

## 0 先定三件事

问句里没说清就先问，不要带着歧义往下走：

- **口径**：「负荷」是瞬时值还是均值？「上半年」含不含 6 月 30 日？
- **粒度**：一行代表什么——一个站一天，还是一个站一个月？
- **范围**：哪些要排除（试运行站、作废单、内部测试账号）？

多个数据源先 `sql_sources` 看有什么，不要猜源名。

## 1 值落地：把问句里的词对到库里的真实写法

DeepEye-SQL 的 Semantic Value Retrieval。原文用向量库，**本实现按用户要求不接 RAG**，改成词面抽关键词 + 对活库采样，一样是数据落地的：

1. 从问句里挑出**实体词**：地名、站名、设备类型、状态词、专业名词。数量词、时间词不用采。
2. 对每个关键词，在可疑的列上 `sql_values <表> <列> --keyword <词>` 采样。
3. 采到了 → 用**采到的原文**写进 SQL；采不到 → 换列采、或者放宽关键词（「江北」而不是「江北新区」）。

**采不到就别硬写。** 关键词一个都对不上时，说明要么表选错了，要么这个词是业务口径而不是数据值——去查 wiki。

标识符和值一律**原样抄**：不做简繁转换、不改大小写、不去空格。库里是「江北新区」就不能写「江北区」。

## 2 三路模式链接

DeepEye-SQL 的 Robust Schema Linking：三条路各有各的盲区，**并集**才靠得住。

表多的时候先用 `sql_tables <问句>` 按词面打分收窄候选（这一步替代原文的 BM25），再对收窄后的子集 `sql_schema --tables a,b,c --samples 3` 拿 M-Schema。

### 路 A 直连

给自己看：问句 + M-Schema + 第 1 步采到的值 → 直接列出相关的表和列，每个都说一句为什么相关。

盲区：问句复杂或列名有歧义时不可靠。

### 路 B 反向

**先写一版草稿 SQL，再从这版 SQL 里把表名列名扒出来。** 写代码这件事模型比做模式分析更熟，所以草稿常常能挖出直连漏掉的中间表和子查询里的列。

三条硬规矩：
- 草稿**不执行**、**不当答案**、**不进候选池**。它唯一的用途是贡献表列名。
- 从草稿里扒名字要看全：FROM、JOIN、WHERE、GROUP BY、ORDER BY、子查询和 CTE 里的都算。
- 扒出来的名字要回 M-Schema 核对，草稿里编出来的表列直接扔掉。

### 路 C 值证

第 1 步在哪一列采到了问句里的词，那一列就相关。这是**数据说话**的一路：几个列名都像的时候（`region` / `district` / `area_name`），只有真的存着「江北新区」那一列是对的。

## 3 并集 + 闭包（这一步最容易漏）

三路的并集是**一堆孤岛**：表都在，但表之间没有边，JOIN 无从下手。

所以必须按 FK 补齐：并集里任意两张表之间，只要 M-Schema 的 `【Foreign keys】` 里有连接关系，就把对应的主键/外键列**加进来**，哪怕问句完全没提这些列。中间表（只有两个 FK 的关联表）也要补。

补完自查：**从任意一张表出发，能不能顺着 FK 走到其他每一张表？** 走不到就是还缺表或缺列，回第 2 步。

## 4 业务口径查 wiki

表义、指标定义、同义词、默认排除规则——`wiki_search`。

- 查到了：在最终结论里写明出处，别让口径来源不明。
- 没查到：**问用户，不要自己发明**。「有效台区」「统调负荷」这类词各家定义不一样，猜错了整份报告都是错的。
- 用户给了新口径：顺手 `wiki_add` 存一页，下次不用再问。

## 5 收口条件

下面每条都过了才进第 2 阶段：

- [ ] 口径、粒度、范围三件事都有明确答案（用户说的，或 wiki 里查到的，或明确标注为假设）
- [ ] 每张表、每个列都在 `sql_schema` 的输出里出现过——没有一个是猜的
- [ ] 问句里的实体词都采到了真实值，或者明确说明了为什么采不到
- [ ] 表集合按 FK 闭包连通
- [ ] 时间字段的类型和格式看过了（字符串日期要不要补零、有没有时分秒）

## 常见坑

- **只跑路 A 就往下走**：漏中间表最常见的原因。
- **草稿 SQL 当答案**：路 B 的草稿没过检查器、没验口径，直接用等于跳过第 2、3 阶段。
- **看了列名就以为懂了**：`load` 可能是有功也可能是视在，`status=1` 可能是启用也可能是停用。列注释和采样值比列名可信，wiki 比两者都可信。
- **值采样只采一列**：几个列名都像的时候，每个都采一遍才知道数据在哪。
- **闭包只补问句提到的列**：连接键通常问句里根本没提。
