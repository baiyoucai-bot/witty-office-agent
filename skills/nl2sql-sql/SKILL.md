# NL2SQL 第 2+3 阶段：出候选并过检查器

**先想清楚再写 SQL，写完必须有人验。** 自己写自己看会带着确认偏误，所以验的活交给确定性的检查器。

输入：第 1 阶段的链接模式 + 采到的真实值 + 定好的口径。
输出：至少一条过了检查器的 SQL，以及它们各自的写法差异。

## 1 先出查询计划，不出 SQL

SQL-of-Thought 的做法，分两步。

### 1.1 按子句拆问题

把问句拆成子句级的小问题，一条一句话：

- 取哪些字段？（SELECT）
- 从哪张表出发，怎么连到其他表？（FROM / JOIN）
- 过滤条件有哪些？（WHERE）
- 分组维度是什么？（GROUP BY）
- 分组后还要过滤吗？（HAVING）
- 怎么排序、取多少行？（ORDER BY / LIMIT）

用不到的子句写「无」，不要凑。

### 1.2 写查询计划

把上面串成一个**按步骤的自然语言计划**，说清每一步做什么、为什么。

**计划里不许出现 SQL 关键字**。写出 `SELECT` 就是跑偏了——那说明在拼语法而不是在想清楚逻辑。

计划里必须交代的两件事：
- **一行代表什么**：聚合之前的粒度，和聚合之后的粒度。
- **连接会不会放大行数**：一对多的连接，聚合前要不要先去重或先聚合。

## 2 N-version：出 2-3 个结构不同的候选

DeepEye-SQL 的 N-version programming。关键是**结构不同**——调温度采样、改改别名不算，那样的候选会一起错。

三条相互独立的写法路线，挑两到三条：

| 路线 | 怎么写 | 擅长 |
|------|--------|------|
| 骨架式 | 先定 SELECT/FROM/WHERE/GROUP BY 的骨架，再往槽里填列 | 结构清楚的常规查询 |
| 分治式 | 每个子问题写成一个 CTE，最后拼起来 | 嵌套逻辑、多层聚合 |
| 反推式 | 从「结果表长什么样」倒推：先写出最终的列和行，再补出处 | 口径绕、指标定义复杂 |

原文的第二路是 ICL（从示例库里检索相似 SQL）。**本实现按用户要求不接 RAG，没有示例库**，第二路改成分治式；同库的历史成功写法和业务口径从 `wiki_search` 拿。

写候选时守住：
- 每条都自带 `LIMIT`（工具会强制补，但生成时就该带）。
- 显式列名，不写 `SELECT *`——问数要能解释每一列。
- 只用第 1 阶段确认过的表列和采到的真实值。
- 方言按 `sql_sources` 报的来：SQLite/MySQL/PG 用 `LIMIT`，Oracle/DM 用 `FETCH FIRST n ROWS ONLY`，MSSQL 用 `TOP n`。

## 3 过检查器链

每个候选都过一遍：

```
sql_check <sql> <第 1 阶段的 M-Schema 文本> <source>
```

**两个参数都要给全**：模式文本带着可空标记和列类型，是空值段（N）和时间段（T3）唯一的证据来源；`source` 决定用哪个方言查时间函数。少给一个，那几项会直接沉默——不是通过，是没查。

三段级联：**语法 → 逻辑 → 质量**（S / L+T / Q+M+N）。先修致命的，再看隐蔽的。

- **FAIL 必须改**，改完重新过。带着 FAIL 执行等于没验。
- **WARN 可以执行**，但每条要么改掉、要么在最终结论里说明为什么可接受。
- 检查项清单和各自的典型错因见 `nl2sql` 技能的 `references/checkers.md`。

三条 WARN 不许一句「可接受」糊过去，它们的代价是静默错数：
- **N3**（`NOT IN` 碰可空列）会返回空表且不报异常，看起来就像库里没有——改 `NOT EXISTS`，别解释。
- **T3**（日期字面量比带时分秒的列）会丢掉右端点那一整天。
- **M1**（`= (SELECT MAX(…))`）先确认用户要不要并列的那几行，再决定改不改。

## 4 改错先定类

拿到 findings 不要直接改 SQL——**先判这是哪一类错**，类决定改哪里。分类法见 `nl2sql` 技能的 `references/error-taxonomy.md`。

三条动作规则：

| 错在哪类 | 动作 |
|----------|------|
| 模式链接类（表列名错、值写法错） | **回第 1 阶段**。改 SQL 治不了 |
| 逻辑类（连接、聚合、过滤、排序） | 改 SQL，改完重新过检查器 |
| 粒度类（数的是记录还是实体） | 回查询计划，重新想「一行代表什么」 |

**同一个 FAIL 改两轮还在，停手回第 1 阶段。** 反复改同一处通常说明口径就理解错了，不是语法写错了。

## 5 收口条件

- [ ] 有一份不含 SQL 关键字的查询计划
- [ ] 有 ≥2 个**结构不同**的候选（简单查询可以只 1 个，但要说明为什么不用验）
- [ ] 每个候选都过了 `sql_check`，没有 FAIL
- [ ] 剩下的 WARN 每条都有处置说明
- [ ] 每个候选都带 LIMIT、都是显式列名

## 常见坑

- **跳过计划直接写 SQL**：省下的几秒会在改错时十倍还回来。
- **候选只是同一条的变体**：`t1.a` 改成 `a.a` 不是新写法。判断标准是「这两条会不会因为同一个理解错误一起错」。
- **改错不定类**：看到 FAIL 就调 GROUP BY，调到不报错为止——报错没了，数还是错的。
- **拿检查器全过当作对了**：检查器只管机械可判定的部分，口径对不对、值写对没有、数字对不对它都管不到，那要靠第 4 阶段的交叉验证。
