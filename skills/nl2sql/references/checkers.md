# 检查器链

`sql_check` 的三段级联：**语法 → 逻辑 → 质量**。一次过完，不循环。每条给的是可执行的修正方向，不是「可能有问题」。

分组和段的对应关系：语法段 = S；逻辑段 = L + T；质量段 = Q + M + N。三段一次全跑完、一次全报出来——论文是逐段 fail-fast，这里改成一次报全：模型改一轮比来回三轮省，而且看得见全局才不会为了消掉一个 FAIL 引出新的。

FAIL 必须改。WARN 可以执行，但要么改掉、要么在结论里说明为什么可接受。

## 语法段（S）

| 码 | 判什么 | 级别 | 为什么 |
|----|--------|------|--------|
| S1 | 只读违规 | FAIL | 非 SELECT/WITH 开头、含写关键字、多语句、括号不配平。问数只读 |
| S2 | 没有 FROM | WARN | 可能是常量查询，也可能漏了表 |
| S3 | 表名不在 schema 里 | FAIL | 猜表名等于编数据。回去看 `sql_schema` |

S1 会在执行时再拦一遍——检查器是给模型看的提示，`sql_run` 的拒绝才是防线。

## 逻辑段（L）

这段抓的是**能跑通但算错**的，是 BIRD/Spider 上的主要失分点。

| 码 | 判什么 | 级别 | 典型后果 |
|----|--------|------|----------|
| L1 | JOIN 数量 > ON/USING 数量 | FAIL | 缺连接条件 → 笛卡尔积，行数被放大几十倍 |
| L2 | SELECT 有聚合又有裸列，无 GROUP BY | FAIL | SQLite/MySQL 不报错，静默取任意一行；PG 直接报错 |
| L3 | WHERE 里用聚合函数 | FAIL | 聚合后的过滤要放 HAVING |
| L4 | 有除法但没 NULLIF | WARN | 分母为 0 时报错或出空值 |
| L5 | JOIN 后直接 COUNT/SUM，无 DISTINCT | WARN | 一对多关系会把总量放大。**最隐蔽的一类** |
| L6 | 用了未声明的表前缀 | WARN | 别名写错，或漏了一张表 |
| L7 | `ON a = b OR c = d` | WARN | 连接条件带 OR，引擎退化成近似笛卡尔积再过滤，行数会爆 |
| L8 | `ON col IN (SELECT …)` | WARN | 把连接写成了半连接，粒度变了 |
| L9 | ORDER BY 里有聚合但整条没 GROUP BY | FAIL | 聚合把全表压成一行，排序和 LIMIT 都成了摆设 |
| L10 | `ORDER BY <聚合> LIMIT 1` | WARN | 并列第一时只返回一条，另一条被静默丢掉 |

**L5 要特别当心**：`station JOIN load_record` 后 `COUNT(*)` 数的是负荷记录条数，不是变电站个数。这类错误 SQL 能跑、结果是个合理的数字、但答的不是用户的问题。判断方法是问自己「聚合前一行代表什么」。

L2 的裸列会被点名列出，照着补 GROUP BY 就行。

L3 和 L9 只看**顶层**：`WHERE id = (SELECT MAX(id) FROM t)` 里的聚合在子查询里，是合法写法，不报。

L10 碰到时不要自己决定：要么按用户口径加第二排序键定序，要么改成 `LIMIT` 放宽后在结论里说明有并列。

## 时间段（T）

时间函数是跨方言最容易翻车的地方，同一条 SQL 在 MySQL 上对、在 SQLite/PG 上直接报错。方言来自 `sql_check` 的 `dialect` 参数，或 `source` 在 `[nl2sql.sources]` 里登记的方言。**两个都没有就整段跳过**——猜方言会对着正确的 SQL 报 FAIL，比漏报贵。

| 码 | 判什么 | 级别 | 说明 |
|----|--------|------|------|
| T1 | 用了该方言里不存在的时间函数 | FAIL | SQLite 没有 `YEAR()`/`DATE_FORMAT()`/`EXTRACT()`；MySQL 没有 `STRFTIME()`/`DATE_TRUNC()`；PG 没有 `STRFTIME()`/`YEAR()`/`DATEDIFF()` |
| T2 | `STRFTIME/DATE_FORMAT/TO_CHAR` 的结果和裸数字比 | FAIL（sqlite）/ WARN | 这些函数返回文本，SQLite 里文本和数字**永远不相等**，静默返回 0 行 |
| T3 | 带时分秒的列和日期字面量比区间 | WARN | `built_at <= '2025-06-30'` 只取到当天 00:00:00，那一天的数据全丢 |

T1 的名单只列**确定不存在**的函数，拿不准的一律不列。

T2 的修法是给字面量加引号（`= '2025'`）或把左边 `CAST(... AS INTEGER)`，两种都行但要一致。

T3 只在模式文本给出列类型是 `DATETIME/TIMESTAMP` 时才报——手工粘贴的 schema 拿不到类型，这项会沉默。修法是右端点写成 `< '2025-07-01'`。

## 质量段（Q）

| 码 | 判什么 | 级别 | 说明 |
|----|--------|------|------|
| Q1 | 没有行数上限 | WARN | 执行时会自动补，但生成时就该带 |
| Q2 | SELECT * | WARN | 问数要显式列名，否则没法解释结果 |
| Q3 | ORDER BY 没配 LIMIT | WARN | 排序开销白花 |
| Q4 | LIKE 模式里没有 % 或 _ | WARN | 等价于等值比较，可能不是本意 |
| Q5 | DISTINCT 和 GROUP BY 同时出现 | WARN | 通常有一个多余 |

## 极值段（M）

| 码 | 判什么 | 级别 | 说明 |
|----|--------|------|------|
| M1 | `WHERE col = (SELECT MAX(col) …)` | WARN | 论文把它当效率问题，但**改写会改语义**：子查询式返回所有并列行，`ORDER BY … LIMIT 1` 只留一行 |
| M2 | 聚合套聚合，如 `MAX(COUNT(*))` | FAIL | 标准 SQL 不允许。要先在子查询里聚合一次，外层再取极值 |

M1 不是「照改就行」的指令。先确认用户要哪种：要全部并列的就别改，只要一条的再改。

M2 碰到窗口函数（`OVER`）时不报——`MAX(COUNT(*)) OVER ()` 是合法的两层语义。

## 空值段（N）

**只在模式文本明确标了「可空」时才报。** 没有证据一律不报，所以手工粘贴的 schema 拿不到这组保护——这是有意的取舍，`sql_schema` 导出的模式文本才带可空标记。

| 码 | 判什么 | 级别 | 说明 |
|----|--------|------|------|
| N1 | ORDER BY 的排序键可空，且没有守卫 | WARN | 取头尾时先拿到一堆 NULL，`LIMIT 10` 全被 NULL 占满。补 `IS NOT NULL` 或 `NULLS LAST` |
| N2 | `COUNT(<可空列>)` | WARN | 只数非空值。要总行数用 `COUNT(*)`，要非空数就在结论里说清 |
| N3 | `NOT IN (SELECT <可空列> …)` | FAIL（列已知可空）/ WARN | 子查询里出现一个 NULL，整条恒为未知，**返回 0 行且不报任何异常**。改 `NOT EXISTS` |

N3 是这份清单里最危险的一条：它长得完全正常、执行成功、返回空表，看起来就像「库里确实没有」。

## 结果检查（Result）

不在 `sql_check` 里，在 `sql_run` 和 `sql_pick` 里：

- `sql_run` 返回 0 行时，会把这条 SQL 的 WHERE / HAVING / ON 条件**逐条原样列出**（字面量保留，`'江北'` 就显示成 `'江北'`），并给出排查顺序。0 行不是答案。
- `sql_pick` 的最大簇是 0 行时，**不走高置信度快捷路径**。多个写法一致地查空，通常是它们共用了同一个错约束，不是库里真没数据。

定位手段只有一个：**一次只去掉一条约束跑一遍**，看哪一条把结果打空的。

## 改两轮还不过怎么办

同一个 FAIL 改两轮仍在，**不要再改 SQL**。这通常说明第 1 阶段的口径理解就错了——比如把「站的个数」理解成「记录条数」，那么 GROUP BY 怎么调都不对。回去重新确认粒度。

## 检查器管不到什么

说清边界，免得误以为过了检查就等于对：

- **口径对不对**：`WHERE voltage_kv = 220` 语法完美，但用户问的可能是 110kV。检查器不知道用户想什么。
- **值写对没有**：`region = '江北区'` 而库里是 '江北新区'，检查器看不出来。这要靠 `sql_values` 采样。
- **粒度对不对**：L5 只能提示风险，不能判定。
- **数字对不对**：唯一的办法是 `sql_pick` 用不同写法交叉验证，或者换一条路径复算。
