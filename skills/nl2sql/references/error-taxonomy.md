# SQL 错误分类法

改错先定类。**分类决定改哪里**：模式类的错回第 1 阶段，逻辑类的改 SQL，粒度类的重新想「一行代表什么」。

按 SQL-of-Thought 的分类法组织，合并了几个在中文库上不常见的子类。

## 1 模式链接类（回第 1 阶段）

改 SQL 治不了，必须回去看 schema。

- **1.1 表名错**：库里没这张表，或者选了同名的另一张。→ `sql_schema` 重看
- **1.2 列名错**：列不存在，或者张冠李戴（把 `load_mw` 当成 `outage_min`）
- **1.3 选错表**：语法对但答的不是这个问题。多张表有相似列时高发
- **1.4 漏表**：需要连三张表只连了两张，中间表被跳过
- **1.5 值写法错**：`'江北区'` vs 库里的 `'江北新区'`，大小写、简繁、空格、全半角。→ `sql_values` 采样对齐

## 2 连接类

- **2.1 缺 ON**：笛卡尔积。行数暴涨，聚合值离谱
- **2.2 连接键错**：连了不该连的列，结果偏少或偏多
- **2.3 连接类型错**：该 LEFT JOIN 用了 INNER JOIN，**没有匹配记录的实体被静默丢掉**。问「各站的负荷」时，没有负荷记录的站就消失了
- **2.4 连接方向错**：LEFT/RIGHT 弄反，保留的是错的那一边
- **2.5 自连接漏条件**：漏了 `a.id <> b.id`，把自己和自己配上

## 3 聚合与粒度类（最容易出「看似合理的错数」）

- **3.1 GROUP BY 漏列**：SELECT 里的裸列没进 GROUP BY
- **3.2 GROUP BY 多列**：多分了一层，结果被打散
- **3.3 聚合函数错**：该 AVG 用了 SUM，该 COUNT(DISTINCT) 用了 COUNT
- **3.4 连接扇出**：一对多连接后聚合，总量被重复计算放大。→ 先聚合再连，或者用 COUNT(DISTINCT)
- **3.5 粒度错**：数的是记录条数，用户问的是实体个数
- **3.6 HAVING/WHERE 混用**：聚合前后的过滤放错位置

## 4 过滤类

- **4.1 条件漏**：用户说的限定没写进 WHERE
- **4.2 条件多**：加了用户没要求的限制
- **4.3 边界错**：时间区间的开闭。「上半年」含不含 6 月 30 日？`< '2026-07-01'` 和 `<= '2026-06-30'` 在有时分秒时不等价
- **4.4 NULL 处理错**：`col <> 'x'` 会把 NULL 行一起排除掉。要保留就写 `(col <> 'x' OR col IS NULL)`
- **4.5 逻辑运算符错**：AND/OR 优先级，缺括号
- **4.6 合取落错行**：两个条件要求落在同一条记录上，却写成了跨记录

## 5 排序与限量类

- **5.1 排序方向错**：要最高的却 ASC
- **5.2 排序键错**：按名称排而不是按数值
- **5.3 LIMIT 值错**：要 top5 给了 top10
- **5.4 并列被截断**：第 5、6 名数值相同，LIMIT 5 只给一个。要完整并列用 RANK()
- **5.5 缺排序的 LIMIT**：没 ORDER BY 就 LIMIT，取到的是任意行

## 6 嵌套与集合类

- **6.1 子查询返回多行**：用在 `=` 右边会报错，该用 IN
- **6.2 相关子查询漏关联**：内层没引用外层，变成常量
- **6.3 IN/EXISTS 混用**：子查询有 NULL 时 `NOT IN` 恒为空
- **6.4 UNION vs UNION ALL**：UNION 会去重，本来要保留的重复行没了
- **6.5 CTE 引用错**：引用了未定义或已被覆盖的 CTE 名

## 7 表达式与类型类

- **7.1 类型不匹配**：字符串日期直接比较，`'2026-6-1' < '2026-10-1'` 字面序不等于时间序。要补零成 `'2026-06-01'`
- **7.2 整除截断**：`3/2` 在整型下得 1
- **7.3 日期函数方言差异**：SQLite 的 `strftime` 和 MySQL 的 `DATE_FORMAT` 不通用
- **7.4 除零**：分母未防护
- **7.5 单位混用**：分钟和小时、MW 和 kW 直接相加

## 8 方言类

- **8.1 限量语法**：LIMIT / FETCH FIRST / TOP 不通用
- **8.2 字符串拼接**：`||` vs `CONCAT`
- **8.3 标识符引号**：双引号 / 反引号 / 方括号
- **8.4 类型转换**：`CAST` 的目标类型名各方言不同

## 9 语义类（最难自查）

语法完美、能跑、有结果，但答的不是用户的问题。

- **9.1 答非所问**：问趋势给了总量
- **9.2 口径不符**：「负荷」取了瞬时值而用户要的是均值
- **9.3 时间范围不符**：「今年」按自然年还是财年
- **9.4 隐含条件漏**：业务上默认排除的（试运行站、作废单）没排除。这类默认口径查 `wiki_search`
- **9.5 结论超出数据**：数据只支持「同步变化」，却写成了「导致」

## 自查顺序

从**后往前**查，语义类最贵也最容易被跳过：

1. 9 语义类：这条 SQL 答的是用户问的那个问题吗？
2. 3 聚合与粒度类：聚合前一行代表什么？
3. 2 连接类：有实体被 INNER JOIN 悄悄丢掉吗？
4. 4 过滤类：边界和 NULL 呢？
5. 剩下的交给 `sql_check`——它能机械判定的都在 `checkers.md` 里。

## 检查器码对到哪一类

`sql_check` 报出来的码不是结论，是线索。先定类，再决定改哪里：

| 码 | 归到 | 改哪里 |
|----|------|--------|
| L7 / L8 | 2 连接类 | 改 SQL 的 ON 条件 |
| L9 | 3 聚合与粒度类 | 回查询计划：要「谁最多」必须先 GROUP BY |
| L10 / 5.4 | 5 排序与限量类 | 问用户要不要并列的那几行 |
| T1 / T3 | 7.3、8 方言类 | 改 SQL，照 `sql_sources` 报的方言 |
| T2 | 7.1 类型不匹配 | 加引号或 CAST，二选一 |
| M1 | 5.4 并列被截断 | 先确认口径再决定改不改 |
| M2 | 3 聚合与粒度类 | 拆两层：子查询先聚合，外层取极值 |
| N1 | 4 过滤类 + 5 排序类 | 补 `IS NOT NULL` 或 `NULLS LAST` |
| N2 | 3.x 计数口径 | `COUNT(*)` 还是 `COUNT(col)`，在结论里写清 |
| N3 | 6.3 IN/EXISTS 混用 | 改 `NOT EXISTS` |
| Result（0 行） | **先怀疑 1.5 值写法错** | 回第 1 阶段 `sql_values` 采样，别改 SQL |

最后一行最重要：**0 行几乎从来不是「库里没有」**，而是某条约束写歪了。1.5 值写法错、7.1 类型不匹配、6.3 `NOT IN` 碰 NULL 这三类都会返回空表且不报任何异常。
